# Learning notes 00: Foundations (Phase 0)

What we built in Phase 0, and the Kubernetes and Go ideas behind it.

## 1. What is an operator?

An operator is a program that runs inside Kubernetes and keeps doing one job:

> Compare what the user **asked for** (desired state) with what **exists** (actual state), and make changes until they match.

A thermostat is a good mental model. You set 22°C (desired). It measures 19°C (actual). It turns the heater on. It keeps checking, forever.

Kubernetes itself works this way. When you create a Deployment with `replicas: 3`, a built-in controller sees 0 pods and creates 3. If one pod dies, it creates another. That loop is called the **reconcile loop**.

An operator is just **your own controller for your own kind of object**. Ours will watch `Release` objects and move services to the versions the Release asks for, in the right order.

```
 you write YAML        Kubernetes API         our operator
 ┌────────────┐       ┌─────────────┐       ┌────────────────────┐
 │ kind:      │ apply │  stores the │ watch │ Reconcile():       │
 │  Release   │──────►│  Release    │──────►│  read desired      │
 └────────────┘       └─────────────┘       │  read actual       │
                             ▲              │  change Deployments│
                             └──────────────┤  write status      │
                                  update    └────────────────────┘
```

## 2. CRD: teaching Kubernetes a new word

Out of the box, Kubernetes knows `Pod`, `Deployment`, `Service` and so on. It has never heard of a `Release`.

A **CustomResourceDefinition (CRD)** teaches it. After `make install`, the cluster accepted this:

```
releases.delivery.releasetrain.io   Namespaced   v1alpha1
```

How to read that name:

| Part | Value | Meaning |
|---|---|---|
| Group | `delivery.releasetrain.io` | A namespace for our APIs, like a Go package path. Uses a domain so it never clashes with someone else's `Release` |
| Version | `v1alpha1` | `alpha` means the API can still change. Later: `v1beta1`, then `v1` |
| Kind | `Release` | The type name you write in YAML as `kind: Release` |
| Plural | `releases` | What you type in `kubectl get releases` |

In YAML that becomes:

```yaml
apiVersion: delivery.releasetrain.io/v1alpha1
kind: Release
```

### The first error was a lesson

When we applied the sample, Kubernetes answered:

```
The Release "release-sample" is invalid: spec: Required value
```

Our operator wasn't even running. **Kubernetes rejected it by itself**, because a CRD contains a schema (OpenAPI v3) and the sample had an empty `spec`. This is a big advantage of CRDs: bad input is refused at the door, before our code ever sees it. In Phase 1 we design that `spec`.

## 4. Go concepts in the generated code

All of these appear in [release_types.go](../../api/v1alpha1/release_types.go) and [release_controller.go](../../internal/controller/release_controller.go).

### Packages and imports
```go
package v1alpha1

import (
    metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
)
```
Every Go file belongs to a package (a folder). `import` pulls in other packages. `metav1` is an **alias**: a short name for a long import path.

### Structs and struct tags
```go
type ReleaseSpec struct {
    Foo *string `json:"foo,omitempty"`
}
```
- A `struct` is a group of fields, like a class with only data.
- The text in backticks is a **struct tag**. It tells Go's JSON/YAML conversion that this field is called `foo` in YAML.
- `omitempty`: leave it out of the output when empty.
- `*string` is a **pointer** to a string. It lets us tell "not set" (`nil`) apart from "set to empty" (`""`). Kubernetes APIs use this a lot for optional fields.
- Capitalised names (`Foo`, `ReleaseSpec`) are **exported**, meaning visible outside the package. Lowercase means private.

### Embedding
```go
type Release struct {
    metav1.TypeMeta   `json:",inline"`
    metav1.ObjectMeta `json:"metadata,omitzero"`
    Spec   ReleaseSpec
    Status ReleaseStatus
}
```
A field with only a type and no name is **embedded**. `Release` gets all of `ObjectMeta`'s fields (name, namespace, labels...) as if they were its own, so you can write `release.Name`. This is how every Kubernetes object gets `apiVersion`, `kind` and `metadata`.

**Spec vs Status** is the most important Kubernetes convention:
- `Spec` = what the **user** wants. Users write it.
- `Status` = what the **operator** observed. Only the operator writes it.

### Methods and receivers
```go
func (r *ReleaseReconciler) Reconcile(ctx context.Context, req ctrl.Request) (ctrl.Result, error) {
```
- `(r *ReleaseReconciler)` makes this a **method** on `ReleaseReconciler`. `r` is like `self` in Python.
- Go functions can **return several values**. Here: a result and an `error`.
- Go has no exceptions. Errors are ordinary return values that you check: `if err != nil { return ..., err }`. You'll write this line hundreds of times.
- `ctx context.Context` carries deadlines and cancellation through a call chain. Kubernetes code passes it everywhere.

### Markers: comments that generate code
```go
// +kubebuilder:subresource:status
// +kubebuilder:rbac:groups=delivery.releasetrain.io,resources=releases,verbs=get;list;watch
```
To Go these are plain comments. `controller-gen` (run by `make manifests`) reads them and generates YAML: the CRD schema, validation rules and RBAC permissions. In Phase 1 we'll use markers like `+kubebuilder:validation:MinItems=1` to validate Releases.

## 6. Exercises (about an hour)

Do these yourself; that's where the learning sticks.

1. **Ask Kubernetes about your type.**
   ```bash
   kubectl explain release
   kubectl explain release.spec
   ```
   The documentation comes from the comments in `release_types.go`.

2. **Make the sample valid.** Edit `config/samples/delivery_v1alpha1_release.yaml` so `spec` contains `foo: hello`, then:
   ```bash
   kubectl apply -f config/samples/delivery_v1alpha1_release.yaml
   kubectl get releases
   kubectl get release release-sample -o yaml
   ```

3. **Watch the controller react.** In `Reconcile`, change `_ = logf.FromContext(ctx)` to:
   ```go
   log := logf.FromContext(ctx)
   log.Info("Reconciling Release", "release", req.NamespacedName)
   ```
   Then run `make run` in one terminal. In a second terminal, edit the Release (`kubectl edit release release-sample`). Each change prints a log line. That is the reconcile loop, live.

4. **See code generate YAML.** Add a field to `ReleaseSpec`:
   ```go
   // owner is the team responsible for this release
   // +kubebuilder:validation:MinLength=2
   Owner string `json:"owner"`
   ```
   Run `make manifests` and look at the diff in `config/crd/bases/`. Then try applying a Release with `owner: x` and see the rejection. Undo the change afterwards with `git checkout -- api config`.

5. **Go basics.** Work through [A Tour of Go](https://go.dev/tour/) sections *Basics* and *Methods and interfaces*. About 2 hours, and it covers everything in this note.

## 7. Glossary

| Term | Meaning |
|---|---|
| Desired state | What the user asked for (`spec`) |
| Actual state | What really exists in the cluster |
| Reconcile | One pass of "compare and fix" |
| Controller | Code that runs the reconcile loop for one kind of object |
| Operator | One or more controllers plus CRDs that automate an application or workflow |
| CRD | CustomResourceDefinition: adds a new object type to Kubernetes |
| CR | Custom Resource: one object of that type, like one `Release` |
| GVK | Group, Version, Kind: the full name of a type |
| envtest | A real Kubernetes API server and etcd started just for tests, without nodes |
| kind | Kubernetes IN Docker: a full local cluster |
| controller-runtime | The Go library Kubebuilder builds on; does the watching, caching and queueing for us |
